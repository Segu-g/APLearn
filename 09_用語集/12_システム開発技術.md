| **ボトムアップテスト** [📖](../01_テクノロジ系/09_システム開発技術.md#結合テストの方法)<br><sub>bottom-up test</sub> | 下位のモジュールから順に上位のモジュールを結合していく結合テスト。上位の代わりにドライバを使う<br>💡 下位の部品を先に固められる。上位からと下位からを同時に進めるのがサンドイッチテスト |  |
| **回帰テスト（リグレッションテスト）** [📖](../01_テクノロジ系/09_システム開発技術.md#回帰テストリグレッションテスト)<br><sub>regression test</sub> | プログラムの修正・変更によって、変更していない部分に悪影響（デグレード）が出ていないかを確認するテスト<br>💡 保守やリファクタリングの後に必ず行う。何度も繰り返すのでテスト自動化と相性がよい。新機能だけを確認するテストではない |  |

| ★ | **廃棄** [📖](../01_テクノロジ系/09_システム開発技術.md#94-保守の手順形態と廃棄-) | 不要になったシステムを、組織の運用に支障のない状態で停止・解体・除去すること<br>💡 手順は 廃棄計画の立案→利用者への通知→新旧環境の並行運用と教育訓練→廃棄の通知→廃棄関連データの保持とアクセス可能性の確保 |  |

<a id="まぎらわしい用語"></a>

## まぎらわしい用語

| 用語 | 用語 | 違い |
|---|---|---|
| **機能要件** | **非機能要件** | 機能要件は「何をするか」（受注登録など）。非機能要件は「どれだけ速く・安全に・止まらずに」など機能以外の品質や制約。 |
| **DFD** | **アクティビティ図** | DFD はデータの流れと処理を表し、処理の順序や分岐は表せない。アクティビティ図は処理の流れを分岐・並行処理・同期を含めて表す。 |
| **汎化** | **集約** | 汎化は共通部分を上位クラスにまとめる is-a の関係。集約は部分を組み合わせて全体を作る part-of の関係。 |
| **オーバーライド** | **オーバーロード** | オーバーライドはサブクラスで同じ名前・同じ引数の操作を定義し直すこと。オーバーロードは同じ名前で引数の異なる操作を複数定義すること。 |
| **モジュール強度（凝集度）** | **モジュール結合度** | 強度はモジュール内部の結び付きで高いほどよい。結合度はモジュール間の結び付きで低いほどよい。 |
| **ドライバ** | **スタブ** | ドライバは未完成の上位モジュールの代役で、ボトムアップテストで使う。スタブは未完成の下位モジュールの代役で、トップダウンテストで使う。 |
| **命令網羅** | **判定条件網羅（分岐網羅）** | 命令網羅（C0）はすべての命令を1回以上実行する。判定条件網羅（C1）はすべての判定の真と偽を1回以上実行し、命令網羅より強い。 |
| **同値分割** | **境界値分析（限界値分析）** | 同値分割は同値クラスから代表値を1つずつ選ぶ。境界値分析はクラスの境界とその前後の値を選ぶ。 |
| **ホワイトボックステスト** | **ブラックボックステスト** | ホワイトボックスは内部構造（命令・分岐）に着目し、主に単体テストで使う。ブラックボックスは仕様（入出力）に着目し、機能の漏れを見つけられる。 |
| **ウォークスルー** | **インスペクション** | ウォークスルーは作成者が主導し、成果物を順に追って確認する。インスペクションはモデレーターが主導し、役割・手順を決めて公式に記録する。 |
| **検証（verification）** | **妥当性確認（validation）** | 検証は仕様（要件）どおりに作ったかの確認。妥当性確認は利用者が本当に必要とするものを作ったかの確認。 |
| **適応保守** | **完全化保守** | 適応保守は OS 更新や法改正など環境の変化への対応。完全化保守は問題がなくても性能や保守性を改善する保守。 |
| **是正保守** | **予防保守** | 是正保守は表面化した不具合を直す事後の保守。予防保守は表面化する前の潜在的な欠陥を直す保守。 |
| **FTA** | **FMEA** | FTA はトップ事象から原因へトップダウンに木構造で展開する。FMEA は部品の故障モードからシステムへの影響をボトムアップに評価する。 |
| **カナリアリリース** | **ブルーグリーンデプロイメント** | カナリアリリースは一部の利用者から段階的に公開する。ブルーグリーンは本番環境を2系統用意し、一気に切り替えて切り戻しも容易にする。 |

<a id="一問一答"></a>

## 一問一答（★★★）

説明を読んで用語を答えてください。クリックすると答えが開きます。

<details><summary>Q1. 性能・可用性・セキュリティ・運用保守性など、機能以外の品質や制約に関する要件</summary>

**非機能要件**（non-functional requirements）
</details>

<details><summary>Q2. 単位時間当たりに処理できる仕事の量（件数）</summary>

**スループット**（throughput）
</details>

<details><summary>Q3. 必要なときにシステムを使える度合い。稼働率で表すことが多い</summary>

**可用性（アベイラビリティ）**（availability）
</details>

<details><summary>Q4. 業務やシステムを、データの流れ（矢印）・プロセス（○）・データストア（＝）・外部実体（□）の4記号で表す図</summary>

**DFD**（Data Flow Diagram）
</details>

<details><summary>Q5. 業務で扱うデータを、実体（エンティティ）と実体間の関連（リレーションシップ）で表す図</summary>

**E-R 図**（Entity-Relationship diagram）
</details>

<details><summary>Q6. データの重複や更新時の矛盾をなくすため、関数従属性にもとづいて表を分割すること</summary>

**正規化**（normalization）
</details>

<details><summary>Q7. オブジェクト指向の分析・設計で使う、クラス図・シーケンス図などを定めた標準のモデリング言語</summary>

**UML**（Unified Modeling Language）
</details>

<details><summary>Q8. クラスの属性・操作と、クラス間の関係（関連・汎化・集約など）を表す UML の図</summary>

**クラス図**（class diagram）
</details>

<details><summary>Q9. クラス図などで、関連する相手のインスタンスがいくつ対応するかを示す表記（1、0..1、0..*、1..* など）</summary>

**多重度**（multiplicity）
</details>

<details><summary>Q10. 処理（アクティビティ）の流れを、分岐・並行処理・同期を含めて表す UML の図</summary>

**アクティビティ図**（activity diagram）
</details>

<details><summary>Q11. 条件の組合せと、それぞれに対して実行する動作を表形式にまとめたもの</summary>

**決定表（デシジョンテーブル）**（decision table）
</details>

<details><summary>Q12. システム及びソフトウェア製品の品質モデルの規格。製品品質を8特性、利用時の品質を5特性で定める</summary>

**JIS X 25010**（SQuaRE: Systems and software Quality Requirements and Evaluation）
</details>

<details><summary>Q13. 1つのモジュールの内部の結び付きの強さ。高いほど独立性が高く、よい</summary>

**モジュール強度（凝集度）**（module strength / cohesion）
</details>

<details><summary>Q14. モジュールどうしの結び付きの強さ。低いほど独立性が高く、よい</summary>

**モジュール結合度**（module coupling）
</details>

<details><summary>Q15. 必要なデータ項目だけを引数で受け渡す結合。結合度が最も低く望ましい</summary>

**データ結合**（data coupling）
</details>

<details><summary>Q16. データ（属性）と操作を一体にし、内部の詳細を外部から隠すこと（情報隠蔽）</summary>

**カプセル化**（encapsulation）
</details>

<details><summary>Q17. スーパークラスの属性や操作を、サブクラスが引き継ぐこと</summary>

**継承（インヘリタンス）**（inheritance）
</details>

<details><summary>Q18. 同じメッセージを送っても、受け取ったオブジェクトのクラスごとに異なる動作をすること（多相性）</summary>

**多態性（ポリモーフィズム）**（polymorphism）
</details>

<details><summary>Q19. 作成者が説明役となり、参加者が成果物の処理を順に追って（机上で動かして）誤りを探すレビュー</summary>

**ウォークスルー**（walkthrough）
</details>

<details><summary>Q20. モデレーター（進行役）が主導し、役割・手順・チェックリストを決めて公式に行うレビュー</summary>

**インスペクション**（inspection）
</details>

<details><summary>Q21. 結合テストで、未完成の上位モジュールの代わりに下位モジュールを呼び出すテスト用モジュール</summary>

**ドライバ**（driver）
</details>

<details><summary>Q22. 結合テストで、未完成の下位モジュールの代わりに呼び出されるテスト用モジュール</summary>

**スタブ**（stub）
</details>

<details><summary>Q23. プログラムの内部構造（分岐や命令）に着目してテストケースを作る技法</summary>

**ホワイトボックステスト**（white box testing）
</details>

<details><summary>Q24. すべての命令を少なくとも1回は実行するようにテストケースを作る網羅基準（C0）</summary>

**命令網羅**（statement coverage）
</details>

<details><summary>Q25. すべての判定について、真と偽の両方を少なくとも1回ずつ実行する網羅基準（C1）</summary>

**判定条件網羅（分岐網羅）**（decision coverage / branch coverage）
</details>

<details><summary>Q26. 内部構造を見ずに、仕様（入力と出力）に着目してテストケースを作る技法</summary>

**ブラックボックステスト**（black box testing）
</details>

<details><summary>Q27. 入力を同じ扱いになるグループ（同値クラス）に分け、各クラスから代表値を1つずつ選んでテストする技法（同値分析法）</summary>

**同値分割**（equivalence partitioning）
</details>

<details><summary>Q28. 誤りが起きやすい同値クラスの境界の値と、その前後の値をテストデータにする技法</summary>

**境界値分析（限界値分析）**（boundary value analysis）
</details>

<details><summary>Q29. 既知のエラーをわざと埋め込んでテストし、その発見率から残っている固有エラーの数を推定する方法</summary>

**エラー埋込法**（error seeding）
</details>

<details><summary>Q30. 上位のモジュールから順に下位のモジュールを結合していく結合テスト。下位の代わりにスタブを使う</summary>

**トップダウンテスト**（top-down test）
</details>

<details><summary>Q31. 下位のモジュールから順に上位のモジュールを結合していく結合テスト。上位の代わりにドライバを使う</summary>

**ボトムアップテスト**（bottom-up test）
</details>

<details><summary>Q32. プログラムの修正・変更によって、変更していない部分に悪影響（デグレード）が出ていないかを確認するテスト</summary>

**回帰テスト（リグレッションテスト）**（regression test）
</details>

<details><summary>Q33. 予期しないデータ（ファズ）を大量に自動生成して入力し、異常終了などから未知の脆弱性を見つけるテスト手法</summary>

**ファジング**（fuzzing）
</details>

<details><summary>Q34. 発注者（利用者）が、納品されたシステムが要件どおりかを確認して受け入れるためのテスト</summary>

**受入れテスト**（acceptance test）
</details>

<details><summary>Q35. 運用中に見つかった不具合（欠陥）を修正する保守</summary>

**是正保守**（corrective maintenance）
</details>

<details><summary>Q36. 不具合として表面化する前に、潜在的な欠陥を見つけて修正する保守</summary>

**予防保守**（preventive maintenance）
</details>

<details><summary>Q37. 法改正や OS の更新など、ソフトウェアを取り巻く環境の変化に合わせて修正する保守</summary>

**適応保守**（adaptive maintenance）
</details>

<details><summary>Q38. 故障ではなく、性能や保守性などを改善するために行う保守</summary>

**完全化保守**（perfective maintenance）
</details>

<details><summary>Q39. 望ましくない事象（トップ事象）から、その原因を AND・OR で木構造にトップダウンに展開して分析する手法</summary>

**FTA**（Fault Tree Analysis）
</details>

<details><summary>Q40. 部品・工程ごとに起こりうる故障モードを洗い出し、システムへの影響をボトムアップに評価する手法</summary>

**FMEA**（Failure Mode and Effects Analysis）
</details>
