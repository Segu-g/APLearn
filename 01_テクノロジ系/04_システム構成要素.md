## 1. システムの処理形態と構成方式

### 1.1 処理形態 ★

| 形態 | 内容 | 例 |
|---|---|---|
| **集中処理** | 1台のホストコンピュータで集中して処理 | 従来のメインフレーム |
| **分散処理** | 複数のコンピュータに処理を分担 | クライアントサーバシステム |
| **バッチ処理** | データを一定期間ためてから一括処理 | 月末の給与計算 |
| **リアルタイム処理** | 発生と同時に即時処理 | 座席予約、ATM |
| 対話型処理 | 利用者と画面でやり取りしながら処理 | Web アプリケーション |

### 1.2 クライアントサーバシステム ★★

**クライアントサーバシステム**とは、サービスを要求する **クライアント** と、サービスを提供する **サーバ** に役割を分けたシステムです。

**3層クライアントサーバシステム** は、処理を3つの層に分けることで、各層を独立して変更しやすくします。

```mermaid
flowchart LR
  P["プレゼンテーション層<br/>（画面・入出力）<br/>Web ブラウザ"] --> F["ファンクション層<br/>（業務ロジック）<br/>アプリケーションサーバ"]
  F --> D["データ層<br/>（データ管理）<br/>データベースサーバ"]
```

| 用語 | 意味 |
|---|---|
| **シンクライアント** | クライアント側には最低限の機能だけを持たせ、処理やデータをサーバ側で管理する方式。情報漏えい対策になる |
| **ストアドプロシージャ** | よく使う SQL 処理をデータベースサーバに登録しておき、クライアントからは名前で呼び出す。**通信量（ネットワーク負荷）を減らせる** |
| **RPC**（Remote Procedure Call） | 別のコンピュータ上の手続を、ローカルの手続のように呼び出すしくみ |
| ピアツーピア（P2P） | サーバとクライアントの区別なく、対等な端末同士が直接通信する方式 |

シラバスでは3層の名称を **プレゼンテーション層**（画面）・**ファンクション層**（業務ロジック）・**データベースアクセス層**（データ管理）と呼びます。

**2層と3層の比較**

| 項目 | **2層クライアントサーバ** | **3層クライアントサーバ** |
|---|---|---|
| 構成 | クライアント（画面＋業務ロジック）とサーバ（DB） | 画面・業務ロジック・DB アクセスを分離 |
| 業務ロジックの変更 | **全クライアントのプログラムを入れ替える** 必要がある | アプリケーションサーバだけを変更すればよい |
| クライアントの負荷 | 大きい（ファットクライアント） | 小さい（Web ブラウザだけでもよい） |
| ネットワーク負荷 | クライアントと DB 間で大量の SQL が往復しやすい | 業務ロジックと DB が近く、クライアントとの通信は結果だけ |

**クライアントサーバシステムの評価の観点**

| 観点 | 内容 |
|---|---|
| **ローカル処理の応答速度** | 入力チェックなど手元で済む処理は、クライアントで行えばサーバとの通信なしに速く応答できる |
| **コスト性能比** | 安価な PC やサーバを組み合わせ、汎用機より費用あたりの性能を高めやすい |
| **柔軟性** | サーバやクライアントを個別に追加・交換でき、規模の変化に対応しやすい |
| **管理責任** | 機器やデータが分散するため、誰がどこを管理するかの責任範囲が曖昧になりやすい |
| **サーバへの利用集中** | 利用者が増えると特定のサーバに処理が集中し、ボトルネックになる |

### 1.3 高信頼化のためのシステム構成 ★★★

| 構成 | 内容 | 特徴 |
|---|---|---|
| **シンプレックスシステム** | 冗長化しない1系統だけの構成 | 安価だが、故障するとシステム停止 |
| **デュアルシステム** | **2系統で同じ処理を同時に行い、結果を照合** する | 信頼性が高い。故障時は片系で処理を継続 |
| **デュプレックスシステム** | **主系（現用系）と待機系** を用意し、通常は主系だけで処理 | 主系の故障時に待機系へ切り替える |

デュプレックスシステムの待機系の状態による分類：

| 方式 | 待機系の状態 | 切替え時間 |
|---|---|---|
| **ホットスタンバイ** | 待機系も起動済みで、主系と同じ状態で待機 | **短い** |
| ウォームスタンバイ | OS は起動しているが、業務アプリケーションは未起動など | 中程度 |
| **コールドスタンバイ** | 待機系は停止中、または別業務に使用中 | **長い** |

💡 **覚え方**：「デュ**アル**＝**ある**（2つとも動いて照合）、デュ**プレックス**＝**控え** の選手がベンチにいる」。

### 1.4 クラスタと負荷分散 ★★

**クラスタリング**とは、複数のサーバを連携させて、1台のサーバのように見せる技術です。

| 種類 | 目的 | 内容 |
|---|---|---|
| **HA クラスタ**（High Availability：高可用性） | 可用性の向上 | 稼働中のサーバが故障したら、別のサーバが処理を引き継ぐ（**フェールオーバ**）。復旧後に元のサーバへ戻すことを **フェールバック** という |
| **負荷分散クラスタ** | 性能の向上 | **ロードバランサ**（負荷分散装置）が要求を複数サーバに振り分ける |
| HPC クラスタ（High Performance Computing） | 計算性能の向上 | 大規模な科学技術計算を並列処理 |

### 1.5 スケールアップとスケールアウト ★★

| 方式 | 内容 | 向いているもの |
|---|---|---|
| **スケールアップ**（垂直スケール） | サーバの CPU やメモリを **高性能化** する | データベースなど、分割しにくい処理 |
| **スケールアウト**（水平スケール） | サーバの **台数を増やす** | Web サーバなど、並列に分けやすい処理 |

逆に、性能を落とす（減らす）ことをそれぞれ **スケールダウン**、**スケールイン** といいます。

### 1.6 マルチプロセッサの結合方式 ★

| 方式 | 内容 |
|---|---|
| **密結合マルチプロセッサ** | 複数の CPU が **主記憶を共有** し、1つの OS で制御する（SMP：対称型マルチプロセッサ） |
| **疎結合マルチプロセッサ** | 各 CPU がそれぞれ主記憶と OS を持ち、通信でつながる（クラスタなど） |
| **タンデム結合** | 複数のプロセッサを **直列** に並べ、前段で前処理（通信制御など）、後段で本処理というように **処理を段階的に分担** する構成 |

プロセッサの結合網（トーラス・ハイパーキューブなど）は 03_コンピュータ構成要素 4.6 を参照してください。

### 1.7 集中処理と分散処理の特徴 ★★

| 項目 | **集中処理システム** | **分散処理システム** |
|---|---|---|
| 構成 | 1台の大型コンピュータですべて処理 | 複数のコンピュータに処理を分担（**分散アーキテクチャ**） |
| 長所 | 運用管理・セキュリティ管理がしやすい。**保守要員を集中化** できる。大型機のため **コスト性能比**（費用あたりの性能）が良いとされた | 1台の故障の影響が限られる。拡張しやすい。部門ごとの要求に合わせやすい（**情報資源の組織への対応性**） |
| 短所 | ホストが故障すると全体が停止。拡張に限界 | 運用管理が複雑。障害箇所の特定が難しい。**管理責任** が分散し曖昧になりやすい。**TCO** が増えることがある |

**分散処理の機能配分の分類**

| 方式 | 内容 | 例 |
|---|---|---|
| **垂直機能分散システム** | 役割の異なる **上下関係（階層）** のコンピュータに機能を配分 | ホスト ⇔ 部門サーバ ⇔ 端末、クライアントサーバ |
| **水平機能分散システム** | **対等** なコンピュータに、**異なる機能** を配分 | 業務ごとに別サーバ（会計サーバ・販売サーバ） |
| **水平負荷分散システム** | **対等** なコンピュータに、**同じ機能** を持たせて負荷を分散 | 同じ Web サーバを複数台並べる |

💡 **機能配分** とは、システム全体の機能を、どのコンピュータに受け持たせるかを決めることです。

### 1.8 その他のシステム構成 ★★

| 用語 | 意味 |
|---|---|
| **ロードシェアリングシステム** | 複数のシステムで **負荷を分担** して処理する構成。1台が故障しても残りで処理を続けられる（負荷分散方式） |
| **シェアードエブリシング** | 複数のサーバが **ディスク（データ）を共有** する構成。どのサーバからも全データにアクセスできるが、共有資源の排他制御が必要 |
| **シェアードナッシング** | 各サーバが **自分専用のディスク** を持ち、何も共有しない構成。データを分割して担当するため **スケールアウトしやすい** |
| **グリッドコンピューティング** | ネットワーク上に分散した多数のコンピュータの処理能力を結集し、仮想的な1台の高性能コンピュータとして使う |
| **エッジコンピューティング** | 利用者や端末に近い場所（エッジ）でデータを処理し、**通信遅延と通信量を減らす** 構成。IoT・自動運転などで活用 |
| **サーバコンソリデーション** | 多数の物理サーバを、仮想化などで **少数のサーバに集約・統合** すること。設置スペース・電力・運用コストを削減 |
| **マイグレーション** | システムやデータを別の環境（新しいハードウェア、OS、クラウドなど）へ **移行** すること。稼働中の VM を止めずに移すのが **ライブマイグレーション** |

**災害対策のバックアップサイト**：本番システムが被災したときに業務を引き継ぐ遠隔地の拠点です。

| 種類 | 待機の状態 | 復旧までの時間 | 費用 |
|---|---|---|---|
| **ホットサイト** | 本番と同じ機器を設置し、データも同期して **常に稼働可能** | **数分〜数時間（最短）** | 最も高い |
| **ウォームサイト** | 機器は設置済みだが、データの復元や起動に手間がかかる | 数時間〜数日 | 中程度 |
| **コールドサイト** | 場所（建物・電源・回線）だけを確保し、**機器は被災後に搬入** | 数日〜数週間（最長） | 最も安い |

⚠️ **ひっかけ注意**：デュプレックスシステムの「ホット／コールド **スタンバイ**」（[1.3](#13-高信頼化のためのシステム構成-)）と、遠隔地の「ホット／コールド **サイト**」を混同しないようにしましょう。考え方（準備度と切替え時間の関係）は同じです。

### 1.9 ハイパフォーマンスコンピューティング（HPC） ★

**HPC**（High Performance Computing）とは、気象予測・創薬・流体解析など、高精度で大量の演算を高速に行う計算処理のことです。

| 用語 | 意味 |
|---|---|
| **スーパーコンピュータ** | HPC 用の超高性能コンピュータ。性能は FLOPS で表す（例：富岳） |
| **大規模並列**（超並列） | 数千〜数百万のプロセッサ（コア）に処理を分割して同時に実行する |
| **アレイプロセッサ** | 多数の演算装置を配列状に並べ、同じ演算を多数のデータに一斉に行う（SIMD 型）プロセッサ |
| **HPC クラスタ** | 多数のコンピュータを高速な LAN などで結び、CPU などの資源を共有して **単一の高性能コンピュータ** として使う構成（[1.4](#14-クラスタと負荷分散-)） |

### 1.10 Web システム ★★

**Web システム**とは、利用者が **Web ブラウザ** から HTTP/HTTPS で **Web サーバ** にアクセスして利用するシステムです。クライアントにブラウザさえあればよく、プログラムの配布が不要なため、3層クライアントサーバシステムの代表的な実現形態になっています。

```mermaid
flowchart LR
  B["Web ブラウザ<br/>（プレゼンテーション層）"] -- "HTTP/HTTPS<br/>リクエスト・レスポンス" --> W["Web サーバ<br/>（静的コンテンツ配信）"]
  W -- "処理の依頼" --> AP["アプリケーションサーバ<br/>（ファンクション層）"]
  AP -- "SQL" --> DB["データベースサーバ<br/>（データベースアクセス層）"]
```

| 構成要素 | 役割 |
|---|---|
| **Web ブラウザ** | HTML・CSS・JavaScript を解釈して画面を表示し、利用者の操作をリクエストとして送る |
| **Web サーバ** | リクエストを受けて HTML・画像などを返す。動的な処理はアプリケーションサーバへ依頼する |
| アプリケーションサーバ | 業務ロジックを実行する |
| データベースサーバ | データを管理し、SQL の要求に応える |

各層の間は、ブラウザ⇔Web サーバが **HTTP（HTTPS）**、アプリケーションサーバ⇔DB サーバが SQL（DB 接続用のプロトコル）で通信します。負荷分散装置で Web サーバを複数台に分ける（水平負荷分散）構成も一般的です。

## 2. クラウドコンピューティング

### 2.1 サービスモデル ★★★

**クラウドコンピューティング**とは、インターネットなどのネットワーク経由で、サーバ・ストレージ・ソフトウェアなどの IT 資源を **必要なときに必要な分だけ** 利用する形態です。

| モデル | 提供されるもの | 利用者が管理する範囲 | 例 |
|---|---|---|---|
| **IaaS**（Infrastructure as a Service） | 仮想サーバ・ストレージ・ネットワークなどの **基盤** | OS、ミドルウェア、アプリケーション、データ | 仮想マシンの貸出し |
| **PaaS**（Platform as a Service） | OS・ミドルウェア・実行環境などの **プラットフォーム** | アプリケーション、データ | アプリ実行環境、DB サービス |
| **SaaS**（Software as a Service） | **アプリケーション** そのもの | データ、利用者設定 | Web メール、グループウェア |

```mermaid
flowchart TB
  subgraph 利用者が管理する範囲
    direction LR
    I["IaaS：OS より上"]
    P["PaaS：アプリケーションとデータ"]
    S["SaaS：データと設定のみ"]
  end
```

| 階層 | オンプレミス | IaaS | PaaS | SaaS |
|---|:-:|:-:|:-:|:-:|
| アプリケーション | 利用者 | 利用者 | 利用者 | 事業者 |
| ミドルウェア・実行環境 | 利用者 | 利用者 | 事業者 | 事業者 |
| OS | 利用者 | 利用者 | 事業者 | 事業者 |
| 仮想化・サーバ・ストレージ・ネットワーク | 利用者 | 事業者 | 事業者 | 事業者 |

**オンプレミス**とは、自社で設備を保有・運用する形態です。

**その他のサービス形態**

- **FaaS**（Function as a Service）／**サーバレス**：利用者はサーバを意識せず、イベント発生時に実行される **関数（プログラム）** だけを用意する形態。実行した分だけ課金されます。
- **DaaS**（Desktop as a Service）：仮想デスクトップ環境をクラウドで提供する形態。

### 2.2 実装（配置）モデル ★

| モデル | 内容 |
|---|---|
| **パブリッククラウド** | 不特定多数の利用者が共有するクラウド |
| **プライベートクラウド** | 特定の組織だけが専有するクラウド |
| コミュニティクラウド | 共通の目的を持つ複数組織で共有するクラウド |
| **ハイブリッドクラウド** | 上記やオンプレミスを組み合わせて使う形態 |
| マルチクラウド | 複数のクラウド事業者のサービスを併用する形態 |

**オートスケール**：負荷に応じて自動的にサーバ台数（資源）を増減する機能です。クラウドの大きな利点の1つです。

## 3. 仮想化とコンテナ

### 3.1 サーバ仮想化 ★★★

**仮想化**とは、物理的な資源（CPU・メモリ・ディスクなど）をソフトウェアで論理的に分割・統合して利用する技術です。1台の物理サーバ上で複数の **仮想マシン（VM）** を動かせます。

| 方式 | 構成 | 特徴 |
|---|---|---|
| **ホスト型** | 物理サーバ → **ホスト OS** → 仮想化ソフト → ゲスト OS | 既存の OS 上で手軽に導入できるが、ホスト OS を経由するため **オーバヘッド** が大きい |
| **ハイパーバイザ型** | 物理サーバ → **ハイパーバイザ** → ゲスト OS | ハイパーバイザがハードウェアを直接制御。オーバヘッドが小さく、サーバ用途で主流 |
| **コンテナ型** | 物理サーバ → ホスト OS → **コンテナエンジン** → コンテナ（アプリ＋ライブラリ） | コンテナは **ホスト OS のカーネルを共有** し、ゲスト OS を持たない。**軽量で起動が速い** |

```mermaid
flowchart TB
  subgraph ハイパーバイザ型
    direction TB
    H1["アプリ"] --- G1["ゲスト OS"]
    H2["アプリ"] --- G2["ゲスト OS"]
    G1 --- HV["ハイパーバイザ"]
    G2 --- HV
    HV --- HW1["ハードウェア"]
  end
  subgraph コンテナ型
    direction TB
    C1["アプリ＋ライブラリ<br/>（コンテナ）"] --- CE["コンテナエンジン"]
    C2["アプリ＋ライブラリ<br/>（コンテナ）"] --- CE
    CE --- OS["ホスト OS（カーネル共有）"]
    OS --- HW2["ハードウェア"]
  end
```

⚠️ **ひっかけ注意**：コンテナは OS のカーネルを共有するため、**ホスト OS と異なる種類のカーネルを必要とする OS は動かせません**（例：Linux のホスト上で Windows カーネルのコンテナを直接動かすことはできない）。

### 3.2 仮想化に関する用語 ★★

| 用語 | 意味 |
|---|---|
| **ライブマイグレーション** | 稼働中の仮想マシンを **停止させずに** 別の物理サーバへ移動させる技術 |
| **オーケストレーション** | 多数のコンテナの配置・起動・監視・スケーリングを自動化すること（例：Kubernetes） |
| **VDI**（Virtual Desktop Infrastructure：デスクトップ仮想化） | 利用者のデスクトップ環境をサーバ上の仮想マシンで動かし、端末には画面だけを転送する |
| **シンプロビジョニング** | 物理容量より大きな論理容量を利用者に見せ、実際に使った分だけ物理容量を割り当てるストレージ仮想化技術 |
| **HCI**（Hyper-Converged Infrastructure） | サーバ・ストレージ・ネットワークを仮想化して、汎用サーバに統合した構成 |
| **SDN**（Software-Defined Networking） | ネットワーク機器の制御をソフトウェアで一元的に行う技術 |
| **IaC**（Infrastructure as Code） | サーバなどのインフラ構成をコードで記述し、自動で構築・管理する考え方 |

## 4. ストレージ構成と RAID

### 4.1 ストレージの接続方式 ★★

| 方式 | 内容 |
|---|---|
| DAS（Direct Attached Storage） | サーバに直接接続するストレージ |
| **NAS**（Network Attached Storage） | LAN に接続し、**ファイル単位** で共有するファイルサーバ専用機 |
| **SAN**（Storage Area Network） | ファイバチャネルなどのストレージ専用ネットワークで、サーバとストレージを **ブロック単位** で接続 |
| **FC-SAN** | **ファイバチャネル**（FC）で構築した SAN。高速・高信頼だが専用機器が必要で高価 |
| **IP-SAN** | **IP ネットワーク（イーサネット）** で構築した SAN。**iSCSI**（SCSI コマンドを IP で運ぶ）などを使い、安価に構築できる |

**データの扱い方によるストレージの分類**

| 種類 | 内容 | 用途 |
|---|---|---|
| **ブロックストレージ** | データを固定長の **ブロック** 単位で管理し、サーバからはディスクとして見える（SAN、クラウドの仮想ディスク） | データベース、VM のディスクなど高速性が必要な用途 |
| ファイルストレージ | フォルダ階層の **ファイル** 単位で管理（NAS） | ファイル共有 |
| **オブジェクトストレージ** | データを、ID とメタデータ（属性情報）を付けた **オブジェクト** として、階層を持たないフラットな空間に格納。HTTP（REST API）でアクセス | 画像・動画・バックアップなど大量の非構造化データ。容量を事実上無制限に拡張しやすい |

### 4.2 RAID ★★★

**RAID**（Redundant Arrays of Independent Disks）とは、複数のディスクを組み合わせて、1台の論理的なディスクとして扱い、**高速化** や **信頼性向上** を図る技術です。

| レベル | 方式 | 実効容量（同容量 n 台） | 耐障害性 | 特徴 |
|---|---|---|---|---|
| **RAID 0** | **ストライピング**（データを分散して書く） | n 台分 | **なし**（1台故障で全データ消失） | 高速。冗長性なし |
| **RAID 1** | **ミラーリング**（同じデータを2台に書く） | 1台分（2台構成時） | 1台故障まで可 | 容量効率 50% |
| RAID 2 | ストライピング＋ **ハミング符号** による誤り訂正用ディスク | 構成による | 1台故障まで可 | 誤り訂正用ディスクが多く必要で、実用されていない |
| RAID 3 / 4 | ストライピング＋ **専用パリティディスク**（RAID 3 はビット／バイト単位、RAID 4 はブロック単位で分散） | n − 1 台分 | 1台故障まで可 | パリティディスクに書込みが集中 |
| **RAID 5** | ストライピング＋ **パリティを分散** | **n − 1 台分** | **1台** 故障まで可 | 最低3台。容量効率と信頼性のバランスが良い |
| **RAID 6** | ストライピング＋ **2種類のパリティを分散** | **n − 2 台分** | **2台** 故障まで可 | 最低4台 |
| **RAID 1+0（10）** | ミラーリングしたものをストライピング | n / 2 台分 | 各ミラーの片側ずつなら複数台可 | 高速かつ高信頼。最低4台 |

```mermaid
flowchart LR
  subgraph RAID5["RAID 5（4台）：パリティ P を各ディスクに分散"]
    D1["ディスク1<br/>A1<br/>B1<br/>C1<br/>Pd"]
    D2["ディスク2<br/>A2<br/>B2<br/>Pc<br/>D1"]
    D3["ディスク3<br/>A3<br/>Pb<br/>C2<br/>D2"]
    D4["ディスク4<br/>Pa<br/>B3<br/>C3<br/>D3"]
  end
```

**具体例**：2 T バイトのディスク4台で構成したときの実効容量

```
RAID 0   ：2 × 4       = 8 T バイト
RAID 1+0 ：2 × 4 ÷ 2   = 4 T バイト
RAID 5   ：2 × (4 − 1) = 6 T バイト
RAID 6   ：2 × (4 − 2) = 4 T バイト
```

**チャンクサイズ**（ストライプサイズ）：ストライピングで各ディスクに順に書き込む **データの区切りの大きさ**（例：64 k バイト）です。小さいと1つのデータが多くのディスクに分散され大きなファイルの転送が速くなり、大きいと小さな読み書きが1台で済み多数の同時アクセスに強くなります。

💡 パリティは XOR で計算します。例えば `A1 ⊕ A2 ⊕ A3 = Pa` としておけば、A2 が失われても `A2 = A1 ⊕ A3 ⊕ Pa` で復元できます。

⚠️ **ひっかけ注意**：RAID はディスク故障への対策であり、**誤操作による削除やウイルス感染への対策（バックアップ）にはなりません**。誤って削除するとすべてのディスクから同時に消えます。

## 5. 信頼性の評価（MTBF・MTTR・稼働率）

### 5.1 RASIS ★

システムの信頼性に関する評価項目の頭文字をとったものを **RASIS**（レイシス）といいます。

| 項目 | 意味 | 指標の例 |
|---|---|---|
| **R**eliability（信頼性） | 故障しにくさ | **MTBF** |
| **A**vailability（可用性） | 使いたいときに使える度合い | **稼働率** |
| **S**erviceability（保守性） | 修理のしやすさ | **MTTR** |
| **I**ntegrity（完全性） | データが矛盾なく正しいこと | — |
| **S**ecurity（安全性・機密性） | 不正アクセスなどからの保護 | — |

### 5.2 MTBF・MTTR・稼働率 ★★★

```mermaid
gantt
  title 稼働と故障の繰返し（イメージ）
  dateFormat X
  axisFormat %s
  section システム
  稼働（MTBF）  :done, a1, 0, 40
  修理（MTTR）  :crit, a2, 40, 45
  稼働（MTBF）  :done, a3, 45, 90
  修理（MTTR）  :crit, a4, 90, 94
```

| 用語 | 意味 | 求め方 |
|---|---|---|
| **MTBF**（Mean Time Between Failures：平均故障間隔） | 故障が直ってから次に故障するまでの **平均稼働時間** | 総稼働時間 ÷ 故障回数 |
| **MTTR**（Mean Time To Repair：平均修復時間） | 故障してから修復するまでの **平均時間** | 総修理時間 ÷ 故障回数 |
| **稼働率** | 全時間のうち稼働している割合 | `MTBF / (MTBF + MTTR)` |
| **故障率** | 単位時間あたりに故障する割合 | `1 / MTBF` |

**具体例1**：MTBF 480 時間、MTTR 20 時間の装置の稼働率

```
稼働率 = 480 / (480 + 20) = 480 / 500 = 0.96
```

**具体例2（運用実績から求める）**：1,000 時間の運用期間中に4回故障し、修理時間の合計が 40 時間だった。

```
総稼働時間 = 1,000 − 40 = 960 時間
MTBF = 960 / 4 = 240 時間
MTTR = 40 / 4  = 10 時間
稼働率 = 240 / (240 + 10) = 240 / 250 = 0.96
```

💡 **稼働率を上げるには**：MTBF を **長く**（壊れにくく）するか、MTTR を **短く**（すぐ直す）します。

**年間停止時間の目安**（1年 = 365日 × 24時間 = 8,760時間）

| 稼働率 | 年間停止時間 |
|---|---|
| 99% | 87.6 時間 |
| 99.9% | 8.76 時間 |
| 99.99% | 約 52.6 分 |

### 5.3 直列システム ★★★

**すべての装置が稼働しているときだけ** システムが稼働する構成です。1つでも故障するとシステムは停止します。

```mermaid
flowchart LR
  IN(("入口")) --> A["装置A<br/>稼働率 a"] --> B["装置B<br/>稼働率 b"] --> OUT(("出口"))
```

```
直列システムの稼働率 = a × b
例：a = b = 0.9 → 0.9 × 0.9 = 0.81
```

**直列システムの MTBF**：故障率（1/MTBF）を足し合わせて逆数をとります。

```
システムの故障率 = 1/MTBF_A + 1/MTBF_B
例：MTBF_A = 1,000 時間、MTBF_B = 1,500 時間
    故障率 = 1/1000 + 1/1500 = 3/3000 + 2/3000 = 5/3000 = 1/600
    システムの MTBF = 600 時間
```

### 5.4 並列システム ★★★

**どれか1つでも稼働していれば** システムが稼働する構成です。**全部が同時に故障** したときだけ停止します。

```mermaid
flowchart LR
  IN(("入口")) --> A["装置A<br/>稼働率 a"]
  IN --> B["装置B<br/>稼働率 b"]
  A --> OUT(("出口"))
  B --> OUT
```

```
並列システムの稼働率 = 1 − (1 − a) × (1 − b)
                     = 1 − （全部が同時に故障している確率）
例：a = b = 0.9 → 1 − 0.1 × 0.1 = 1 − 0.01 = 0.99
例：0.8 の装置を3台並列 → 1 − 0.2³ = 1 − 0.008 = 0.992
```

💡 **覚え方**：「直列は **掛ける**、並列は **1 から（1−稼働率）の積を引く**」。

### 5.5 混合システム ★★★

**手順**：内側の並列部分を1つの装置とみなして稼働率を求め、それを直列計算に使います。

**具体例**：装置A（0.95）→ 並列部分（装置B 0.9 × 2台）→ 装置C（0.98）

```mermaid
flowchart LR
  IN(("入口")) --> A["装置A<br/>0.95"]
  A --> B1["装置B1<br/>0.9"]
  A --> B2["装置B2<br/>0.9"]
  B1 --> C["装置C<br/>0.98"]
  B2 --> C
  C --> OUT(("出口"))
```

```
① 並列部分：1 − (1 − 0.9) × (1 − 0.9) = 1 − 0.01 = 0.99
② 全体（直列）：0.95 × 0.99 × 0.98
              = 0.9405 × 0.98
              = 0.92169 ≒ 0.922
```

### 5.6 n 台中 k 台以上が稼働すればよいシステム ★★

**具体例**：稼働率 a の装置3台のうち、**2台以上** 稼働していればよいシステム

```
3台とも稼働          ：a³
ちょうど2台が稼働    ：3C2 × a² × (1 − a) = 3a²(1 − a)
稼働率 = a³ + 3a²(1 − a) = 3a² − 2a³

a = 0.9 のとき：3 × 0.81 − 2 × 0.729 = 2.43 − 1.458 = 0.972
```

### 5.7 故障率曲線（バスタブ曲線） ★

時間の経過による故障率の変化を表したグラフで、浴槽（バスタブ）の形に似ています。

| 期間 | 故障率 | 原因 |
|---|---|---|
| **初期故障期間** | 高いが次第に減少 | 設計・製造上の欠陥 |
| **偶発故障期間** | 低く一定 | 偶発的な原因 |
| **摩耗故障期間** | 次第に増加 | 部品の摩耗・劣化 |

## 6. 信頼性設計の用語

### 6.1 フォールトトレランス関連の用語 ★★★

| 用語 | 意味 | 例 |
|---|---|---|
| **フォールトトレランス**（耐故障性） | 故障が発生しても、**システム全体として正常に動作を継続** できるようにする考え方 | 構成要素の二重化 |
| **フォールトアボイダンス**（故障回避） | 高品質の部品を使うなどして、**故障そのものを起こさない** ようにする考え方 | 信頼性の高い部品の採用、予防保守 |
| **フェールセーフ** | 故障したときに、**安全な側** にシステムを停止・制御する | 信号機が故障したら赤信号にする |
| **フェールソフト** | 故障したときに、**機能を縮小してでも稼働を続ける** | 複数エンジンの1つが止まっても飛行を続ける |
| **フールプルーフ** | 利用者が **誤操作をしても** 危険が生じない（誤操作できない）ようにする | ドアが閉まっていないと動かない電子レンジ |
| **フォールトマスキング** | 故障の影響を内部で隠し、外部に出さない | ECC メモリによる誤り訂正、多数決回路 |
| **グレースフルデグラデーション**（縮退運転） | 故障箇所を切り離し、性能を落として運転を続けること（フェールソフトを実現する運転） | — |

💡 **覚え方**：「**セーフ＝安全に止まる**」「**ソフト＝柔らかく（縮退して）動き続ける**」「**フール（愚か者）でも大丈夫**」。

```mermaid
flowchart TD
  R["信頼性を高める考え方"] --> FA["フォールトアボイダンス<br/>そもそも故障させない"]
  R --> FT["フォールトトレランス<br/>故障しても動かし続ける"]
  FT --> FS["フェールセーフ<br/>安全側に倒す"]
  FT --> FSO["フェールソフト<br/>機能を縮小して継続"]
  R --> FP["フールプルーフ<br/>人の誤りに備える"]
```

### 6.2 信頼性設計の構成と技術 ★★

| 用語 | 意味 |
|---|---|
| **フォールト** | 故障や欠陥など、システムが正しく動かなくなる **原因**（障害の原因となる異常） |
| **信頼性ブロック図** | 構成要素を箱で表し、直列・並列のつながりでシステムの稼働条件を表した図。稼働率計算に使う（[5.3](#53-直列システム-)〜[5.5](#55-混合システム-)） |
| **フォールトトレラントシステム** | 構成要素を多重化し、故障してもシステム全体は停止しないようにしたシステム |
| **無停止コンピュータ**（ノンストップコンピュータ） | CPU・メモリ・電源などを **すべて多重化** し、故障中も無停止で処理を続けるフォールトトレラントコンピュータ |
| **予備切替** | 現用機が故障したときに **予備機に切り替えて** 処理を継続する方式（デュプレックスシステムの考え方） |
| **並列運転** | 複数の装置を **同時に運転** し、1台が故障しても残りで処理を続ける方式（デュアルシステム、ロードシェアリング） |
| **競合制御** | 複数の処理（系）が同じ資源を同時に使おうとしたときに、排他制御などで調停し整合性を保つこと |
| **クラスタリング** | 複数のサーバを連携させて1つのシステムとして動かし、可用性や性能を高める技術（[1.4](#14-クラスタと負荷分散-)） |
| **UPS**（Uninterruptible Power Supply：無停電電源装置） | 停電時に **蓄電池から一定時間電力を供給** し、その間にシステムを安全に停止させたり自家発電に切り替えたりする |

**クラスタの稼働方式**

| 方式 | 内容 | 特徴 |
|---|---|---|
| **アクティブ-スタンバイ構成** | 1台が処理（アクティブ）、もう1台は待機（スタンバイ）。故障時に待機系へ **フェールオーバ** | 構成が単純。待機系の資源は平常時に遊んでいる |
| **アクティブ-アクティブ構成** | **すべてのサーバが同時に処理** し負荷を分担。1台が故障したら残りが処理を引き継ぐ | 資源を有効に使え性能も高い。ただし故障時は残りの台数で全負荷を処理できる能力が必要 |

## 7. 性能評価

### 7.1 性能の指標 ★★★

| 指標 | 意味 |
|---|---|
| **レスポンスタイム**（応答時間） | 要求を出し終えてから、**最初の応答が返ってくるまで** の時間 |
| **ターンアラウンドタイム** | ジョブを投入してから、**結果をすべて受け取るまで** の時間（バッチ処理で使う） |
| **スループット** | **単位時間あたりの処理量**（例：1秒あたりのトランザクション数 TPS） |

### 7.2 性能評価の手法 ★★

| 手法 | 内容 |
|---|---|
| **ベンチマーク** | 標準的なプログラムを実際に実行して性能を測定・比較する。**SPEC**（CPU 性能：SPECint は整数演算、SPECfp は浮動小数点演算）、**TPC**（トランザクション処理性能：TPC-C など） |
| **モニタリング** | 稼働中のシステムの CPU 使用率、応答時間などを測定する。測定に使うソフトウェアやハードウェアを **システムモニタ** という |
| シミュレーション | システムのモデルを作って模擬実行し、性能を予測する |
| **キャパシティプランニング** | 将来の業務量を予測し、必要な資源（CPU、メモリ、ストレージ、回線）を計画する |
| ギブソンミックス | 科学技術計算用の命令ミックス（命令の出現比率の組合せ） |
| コマーシャルミックス | 事務計算用の命令ミックス |

### 7.3 スループットとボトルネックの計算 ★★

**具体例**：1件のトランザクションで、CPU 処理に 20 ミリ秒、ディスクへのアクセスが3回（1回 15 ミリ秒）必要。CPU とディスクは1台ずつで、CPU 処理とディスクアクセスは並行して実行できるものとする。最大スループットはいくらか。

```
① 1件あたりの各装置の使用時間
   CPU   ：20 ミリ秒
   ディスク：15 × 3 = 45 ミリ秒
② 各装置が1秒間に処理できる件数
   CPU   ：1,000 / 20 = 50 件/秒
   ディスク：1,000 / 45 ≒ 22.2 件/秒
③ システム全体の最大スループット＝最も遅い装置で決まる
   → 約 22 件/秒（ディスクが ボトルネック）
```

**ボトルネック**とは、全体の性能を制約している最も遅い部分のことです。この例ではディスクを2台に増やしてアクセスを分散すると、ディスクの使用時間は 1台あたり約 22.5 ミリ秒、処理能力は約 44 件/秒になり、性能が向上します。

⚠️ 1件あたりの **応答時間**（待ちがない場合）は `20 + 45 = 65 ミリ秒` です。スループットと応答時間を混同しないようにしましょう。待ちが発生する場合は「01_基礎理論」の待ち行列（M/M/1）で計算します。

### 7.4 システムの経済性 ★

**TCO**（Total Cost of Ownership：総保有コスト）とは、システムの導入から廃棄までにかかる費用の総額です。

```
TCO = 初期コスト（イニシャルコスト：ハードウェア・ソフトウェア購入、開発費）
    + 運用コスト（ランニングコスト：保守費、電気代、運用人件費など）
```

| コストの区分 | 内容 | 例 |
|---|---|---|
| **直接コスト** | システムのために **明確に支払う** 費用 | ハードウェア・ソフトウェアの購入費、保守契約料、回線費、運用要員の人件費 |
| **間接コスト** | 帳簿に表れにくい **隠れた費用** | 利用者が操作に迷う時間、利用者同士の教え合い、システム停止による業務の損失 |

⚠️ TCO を評価するときは、初期コストだけでなく運用コストや **間接コスト** まで含めて比較します。初期コストが安くても、運用コストや間接コストが高いと TCO は大きくなります。

### 7.5 キャパシティプランニング ★★

**キャパシティプランニング**とは、システムに求められる処理の種類・量・処理時間などから **必要な資源（CPU、メモリ、ストレージ、ネットワーク）の性能と量を見積もり**、運用開始後も継続的に把握・評価して計画を見直す活動です。

```mermaid
flowchart LR
  A["① 要件の把握<br/>処理件数・ピーク時の負荷<br/>応答時間の目標"] --> B["② サイジング<br/>サーバ・ストレージの<br/>性能諸元を見積もる"]
  B --> C["③ 導入・<br/>プロビジョニング"]
  C --> D["④ モニタリング<br/>使用率・応答時間を測定"]
  D --> E["⑤ 評価・将来予測<br/>不足なら増強を計画"]
  E --> B
```

| 用語 | 意味 |
|---|---|
| **負荷** | システムに与えられる処理量（トランザクション数、同時接続数など）。ピーク時の負荷を基準に見積もる |
| **サイジング** | 性能要件を満たすのに必要なハードウェアの **規模（CPU 数、メモリ量、ディスク容量など）を見積もる** こと |
| **スケールアップ / スケールアウト** | 1台を高性能化して能力を上げる／台数を増やして能力を上げる（[1.5](#15-スケールアップとスケールアウト-)） |
| **容量・能力管理** | 現在と将来の業務に必要な容量・能力を、適切なコストで確保し続ける管理活動（ITIL のキャパシティ管理） |
| **システムパラメータ** | OS やミドルウェアの設定値（バッファサイズ、同時接続数の上限など）。チューニングで性能を調整する |
| **プロビジョニング** | 需要に応じて、サーバ・ストレージ・ネットワークなどの資源を **割り当てて利用可能な状態にする** こと |

**サイジングの計算例**：ピーク時に 1 時間あたり 36,000 件のトランザクションがあり、1件の CPU 処理時間が 0.2 秒。CPU 使用率を 50% 以下に抑えたい。必要な CPU 数はいくつか。

```
① 1秒あたりの件数 = 36,000 ÷ 3,600 = 10 件/秒
② 1秒あたりに必要な CPU 時間 = 10 × 0.2 = 2 秒 → CPU 2 個分（使用率 100% 換算）
③ 使用率 50% 以下にするには 2 ÷ 0.5 = 4 個
```

<details><summary>解答・解説</summary>

**問1　イ**
アはデュアルシステム、ウは負荷分散クラスタ、エはシンプレックスシステムの説明です。

**問2　イ**
PaaS は OS・ミドルウェア・実行環境を事業者が提供し、利用者はアプリケーションとデータを管理します。IaaS は OS から利用者が管理し、SaaS はアプリケーションそのものが提供されます。

**問3　イ**
アはコンテナの性質と逆、ウはハイパーバイザ型の説明、エはライブマイグレーションの説明です。

**問4　イ**
```
RAID 6 の実効容量 = 容量 × (台数 − 2) = 4 × (6 − 2) = 16 T バイト
```

**問5　ア**
```
総稼働時間 = 2,000 − 50 = 1,950 時間
MTBF = 1,950 / 5 = 390 時間
MTTR = 50 / 5 = 10 時間
稼働率 = 390 / (390 + 10) = 390 / 400 = 0.975
（検算：1,950 / 2,000 = 0.975 ✔）
```

**問6　イ**
```
並列部分 = 1 − (1 − 0.8) × (1 − 0.8) = 1 − 0.04 = 0.96
全体 = 0.96 × 0.9 = 0.864
```

**問7　0.993**
```
稼働率 = 3a² − 2a³（a = 0.95）
a² = 0.9025、a³ = 0.857375
3 × 0.9025 − 2 × 0.857375 = 2.7075 − 1.71475 = 0.99275 ≒ 0.993
```

**問8　イ**
機能を縮小して継続するのがフェールソフトです。フェールセーフは安全側に停止・制御する考え方です。

**問9　33 件/秒**
```
CPU：1,000 / 30 ≒ 33.3 件/秒
ディスク：1,000 / 25 = 40 件/秒
最も遅い CPU がボトルネック → 33 件/秒
```

| [フォールトアボイダンス](#61-フォールトトレランス関連の用語-) | 高品質部品などで故障そのものを起こさない考え方 |
| [フェールセーフ](#61-フォールトトレランス関連の用語-) | 故障時に安全側へ停止・制御する考え方 |
| [フェールソフト](#61-フォールトトレランス関連の用語-) | 故障時に機能を縮小して稼働を続ける考え方 |

| [無停止コンピュータ](#62-信頼性設計の構成と技術-) | 全構成要素を多重化し無停止で処理を続けるコンピュータ |
